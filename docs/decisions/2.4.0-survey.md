# Nerospace 2.4.0 — Stage 0 survey

Surveyed 2026-11-18 against the 2.3.1 tree. Private dev notes; not part of the wiki.

Verification levels used below: **source** = read from this repo or from sources jars in its build
caches; **upstream** = read from the Iris source at the named branch; **inferred** = reasoned, not read;
**not run** = needs a render client, which the build agent does not have.

## 1. Reproduction status

Nothing in the player's report was reproduced on a render client. The build agent has no GPU client, so
the shader findings below come from reading the mod and the Iris sources. The owner's in-game checklist
in `docs/SMOKE-2.4.0.md` carries every visual check.

What the sources say about each report:

| Report | Finding | Level |
| --- | --- | --- |
| Space "looks like Earth" with shaders | Every planet dimension type declares `"skybox": "overworld"` (26.x) or `effects: minecraft:overworld` (1.21.1 to 1.21.10). Iris maps a dimension the pack does not name to the pack's overworld programs. | source + upstream |
| No Earth, Moon or Mars in space | The sky is drawn in one cell only (NeoForge 26.3). The other 26 cells show flat dimension colours with or without shaders. | source |
| Shader clouds on the Moon | Same cause as the first row: the pack runs its overworld programs, including its own clouds. The mod already disables vanilla clouds. | source + upstream |
| Launch flames not visible | The plume uses `RenderTypes.eyes` and the lamps use `entityTranslucentEmissive`. Iris routes both to `gbuffers_spidereyes` on every supported version, so they should already draw as emissive entity geometry. How a pack blends them after its deferred passes is pack-dependent. | source + upstream, not run |

Consequence for D15: no render-type change is justified from sources alone. D15 shrinks to D16 (the
ignition burst) plus the owner's in-game check. If the plume is missing under a named pack, that is the
case to bring back.

## 2. Sky hook per cell

GPU API by version (source):

| MC | Vanilla sky entry | GPU API |
| --- | --- | --- |
| 1.21.1 | `LevelRenderer.renderSky(Matrix4f, Matrix4f, float, Camera, boolean, Runnable)` | immediate mode, no `RenderPipelines` |
| 1.21.4 | private `addSkyPass(FrameGraphBuilder, Camera, float, FogParameters)` | `VertexBuffer`, no `RenderPipelines` |
| 1.21.5 | same `addSkyPass` | blaze3d `RenderPass`, no `DynamicUniforms`, no `GpuBufferSlice` |
| 1.21.8 | `addSkyPass(.., Camera, float, GpuBufferSlice)` | blaze3d with `DynamicUniforms` |
| 1.21.10, 1.21.11 | `addSkyPass(.., Camera, GpuBufferSlice)` | as 1.21.8 |
| 26.1.2, 26.2 | `addSkyPass(.., CameraRenderState, GpuBufferSlice)`, multi-call lambda | blaze3d, `ProjectionMatrixBuffer` present |
| 26.3 | same; lambda is `this.skyRenderer.render(skyFog, state)` | `com.mojang.renderpearl.api.*` |

The draw half of `NeoForgePlanetSky` is vanilla API, but it is 26.3-shaped. "One drawing path" therefore
means one class with version blocks, and four distinct backends if every 1.21.x line were to be covered.

Loader hooks (source):

- **NeoForge**: `CustomSkyboxRenderer` exists on 1.21.11, 26.1.2, 26.2 and 26.3 (signature differs:
  `Runnable` fog setup before 26.3, `GpuBufferSlice` on 26.3). 1.21.1 to 1.21.10 have a
  `DimensionSpecialEffects.renderSky` extension with a different signature on almost every line.
- **Forge**: `IForgeDimensionSpecialEffects.renderSky` on 1.21.1 only. Nothing sky-related from 1.21.4 on.
- **Fabric**: `DimensionRenderingRegistry.registerSkyRenderer` in the Fabric API for 1.21.1 to 1.21.8
  (version mapping inferred from jar order); gone after that. No sky hook on 26.x.

D2 decision:

- **26.x, all nine cells: mandatory.** NeoForge keeps `CustomSkyboxRenderer`. Fabric and Forge take a
  client mixin on the sky pass (26.3: `SkyRenderer.render`; 26.1.2 and 26.2: the `addSkyPass` lambda).
- **1.21.x, eighteen cells: shared path only where it ports cheaply and can be verified from sources.**
  A cell that cannot keeps the colour floor. The final per-cell matrix, with the reason for every cell
  left on the floor, is in `docs/HANDOVER-2.4.0.md`.

Two constraints found on the way:

- A sky mixin in `nerospace-common.mixins.json` would also load on NeoForge, because all three loaders
  declare that config and there is no mixin plugin. The Fabric hook goes in `nerospace.mixins.json`; Forge
  needs its own config.
- `SkyAssetsTest` asserts that the `neoforge:custom_skybox` attribute exists only in the NeoForge 26.3
  overlay. Extending the attribute to other versions means updating that test and
  `tools/gen_sky_overlays.py` together.

### 3.2 Public API (upstream)

`net.irisshaders.iris.api.v0.IrisApi`: `isShaderPackInUse()`, `isRenderingShadowPass()`, `getConfig()`
and friends on every version. Revision 3 (1.21.5 to 1.21.11) adds
`assignPipeline(RenderPipeline, IrisProgram)`; revision 4 (26.x) adds shadow variants. **There is no API
for dimension mapping on any version.** `assignPipeline` throws if a pipeline is assigned twice.

### 3.3 Where the dimension is resolved (upstream)

`net.irisshaders.iris.Iris#getCurrentDimension()` returns a
`net.irisshaders.iris.shaderpack.materialmap.NamespacedId`. Same signature on every branch read (1.21.1,
1.21.4, 1.21.5, 1.21.6, 1.21.9, 1.21.11, 26.1, 26.2, 26.3). Three behaviours:

- **A, raw key**: all 1.21.4 and 1.21.5 builds, 1.21.1 up to 1.8.12, and (inferred) 1.21.11 builds
  1.10.0 to 1.10.6.
- **B, effects-based**: if the pack names the id, use it; else `effects: minecraft:the_end` maps to the
  End. 1.21.1 in 1.8.14-beta.1, 1.21.8 from 1.9.2, 1.21.10 from 1.9.4.
- **C, skybox-based**: same pack check, then the dimension type's skybox: `END` maps to the End,
  `OVERWORLD` to the overworld. 1.21.11 from 1.10.7 and all 26.x.

Pack side: `dimension.properties` maps folders to ids (`dimension.<folder>=<ns:path> ...`, only `*` as a
wildcard). Without the file, legacy folders apply (`world0` overworld and everything else, `world-1`
Nether, `world1` End). An unmapped modded dimension gets the overworld programs. Under behaviour C our
`"skybox": "overworld"` is reported as the overworld explicitly.

### 3.4 Mixin targets for D5 and D6

One target covers every version: `Iris#getCurrentDimension`, `@Inject` at `RETURN`, cancellable,
`@Pseudo`, `remap = false`, `require = 0`. The callers compare against the `DimensionId.END` constant by
identity, so the hook must return that constant (read reflectively once, fail-soft).

"The pack names us" (D7): `Iris.getCurrentPack()` then `ShaderPack#getDimensionMap()`; the getter is
missing on 1.21.4 and 1.21.5, where the private field `dimensionMap` exists. Both are read reflectively
and fail soft. A `*` entry does not count as naming us.

No other Iris internals are needed.

### 3.5 Finding that changes D6 and D8

**Reporting a world as the End does not make a pack draw our sky bodies.** Read from the current sources
of three widely used packs: in their End programs the textured sky program outputs a flat colour, or is
black, or discards, unless a pack option is switched on. So on an End-mapped world:

- blue sky and pack clouds go away (asks 1 and 3 are met);
- the Nerospace bodies and stars drawn through the pack's sky programs are flattened or hidden by those
  packs (ask 2 is not met under those packs, by the pack's own design).

This is the D9 "pack hides sky geometry by design" limit, but it applies to the mainstream packs rather
than to an odd one. Options, for the owner:

1. Ship D6 as designed and document the limit in `Shaders.md` (what this build does).
2. On 1.21.5+, route the body pipeline to another pack program with `IrisApi.assignPipeline` (for
   example the textured or beacon-beam program). Untested, pack-dependent, and it moves bodies out of
   the sky pass, so depth and fog behaviour would need a render client to tune.
3. Keep such worlds on the pack's overworld programs when `shaders.drawPlanetSky` is on, accepting the
   pack's blue sky. This contradicts ask 1.

Also from 3.4: on 1.21.5+ any pipeline other than the vanilla `SKY`, `STARS`, `CELESTIAL` and `END_SKY`
is unknown to Iris. The shared sky path uses only those vanilla pipelines, so it needs no assignment.

## 4. Rocket ascent: every read of the launch counters

All in `common/`; the loader trees have none.

| Where | Use |
| --- | --- |
| `RocketEntity.LAUNCH_DURATION` (100) | baseline; was the ascent length |
| `RocketEntity.launchTicks` | server counter, saved as `LaunchTicks`, not synced |
| `RocketEntity.launchAnim` / `launchAnimPrev` | client only, never saved or synced |
| `launchProgress(pt)` | `launchAnim / LAUNCH_DURATION`; feeds `RocketRenderer` → `RocketModel.setupAnim` (legs, staging, plume stretch, fins) |
| `ignition(pt)` | `launchAnim / IGNITION_TICKS` (absolute 12 ticks) |
| `tickPresentation()` | advances `launchAnim`; in descent uses `DescentMath.reversedLaunchAnim(LAUNCH_DURATION, height)` |
| `tick()` | speed `0.08 + 0.5·(t/100)²` × gravity bonus `1.5 − 0.5·factor`; `finishAscent()` at 100 ticks |
| `spawnLaunchParticles()` | pad cloud while `launchAnim < IGNITION_TICKS + 10` |
| `Crew.FLIGHT_TICKS` | `LAUNCH_DURATION + 60 + 8 = 168`; sets the oxygen a launch needs per seat |
| tests | `CrewRocketTest` pins 168; `DescentStateTest` pins `reversedLaunchAnim(100, ..)` |

Findings that shape Stage 3:

- The baseline climb sums to 24.42 blocks, not a flat 24.
- The ascent is **not** `noPhysics`: it uses `move(MoverType.SELF, ..)`, so a ceiling stalls the hull and
  the counter still completes. D14's "existing obstruction rules" are exactly that, and they are kept. A
  96-block climb meets ceilings a 24-block one did not; the wiki says to keep the sky clear.
- `Crew.FLIGHT_TICKS` stays 168 (D13: crew rules unchanged). A 96-block climb lasts 159 ticks, so the
  oxygen budget per seat is about one check short of the real flight. Flagged for the owner in the
  handover rather than changed.
- `CargoRocketEntity` defines no synced data of its own, so appending one field to `RocketEntity` is safe
  for both.
- The mod has no existing use of the vanilla particle setting. Particles spawned through
  `Level.addParticle` are already thinned by it.

## 5. Seams a new world touches

The full list is in `docs/decisions/2.4.0-seams.md`, written from the Luna, Mars and Glacira packages.
The ordered build list for Europa is in `docs/decisions/2.4.0-europa.md`.

Three findings that shape the Europa build:

- No loader Java is per-world. A new world needs no edits in `fabric/`, `forge/` or `neoforge/` Java;
  the only loader-side per-world file is the generated NeoForge dimension-type overlay.
- Hazards do not change with terraform stage in the existing system. Terraforming changes breathability
  and gravity only. D24 is designed within that.
- `PlanetDefinition` carries one `WeatherParams` per planet. D20 asks for two events on Europa; the
  design doc specifies the smallest additive change.
