# Nerospace privacy & telemetry disclosure

Nerospace includes anonymous error reporting so that crashes and bugs caused by the mod can
be found and fixed. It is **on by default** and **opt-out** (see
[How to opt out](#how-to-opt-out)). This page is the full disclosure required by
CurseForge's moderation rules for mods that use an external analytics/error service, and it
documents how the system is designed to comply with the GDPR (EU) and POPIA (South Africa).

## What is collected

When an error **caused by Nerospace code** occurs, a report is sent to
[Sentry](https://sentry.io) (hosted in the **EU** — `ingest.de.sentry.io`) containing:

- the stack trace of the error and the error message (file paths containing your
  operating-system account name are masked before sending),
- the Nerospace version, the loader (NeoForge / Forge / Fabric) and its version, the
  Minecraft version, and whether the game is a client or dedicated server,
- the operating system name/version and Java version,
- the mod's own configuration multipliers (e.g. energy/oxygen/fuel/machine-speed settings),
  so a crash that only happens at non-default balance settings can be reproduced,
- the list of **other loaded mods** (their public ids and versions only), so a crash caused
  by a mod conflict can be identified,
- a short trail of recent in-game mod actions ("breadcrumbs") — for example "launched a
  rocket", "travelled to a dimension", "founded a station" — recorded as generic action
  names plus dimension/slot ids and landing-rule step numbers only (never coordinates,
  inventory, or world data),
- a random event ID generated by Sentry for the individual report.

To measure overall stability and performance, the mod also sends:

- **Release-health sessions:** a count that a play session started and whether it ended
  cleanly or crashed, tagged only with the mod / loader / Minecraft version. Each session
  uses a random identifier that exists only for that single play session and is **not**
  linked to any other session, to your account, or to your machine.
- **Performance samples:** the timing of a small, randomly-sampled fraction of internal mod
  operations (such as a rocket launch or a pipe-network rebuild) — duration and operation
  name only, with no personal data.

## What is NOT collected

- **No IP address** is stored (`sendDefaultPii` is disabled; Sentry discards the sender IP).
- **No username, player UUID, or machine/host name.**
- **No world data, chat, coordinates, inventories, or gameplay analytics** of any kind.
- **No advertising or tracking identifiers** — there is no persistent ID linking reports
  from the same player or machine.
- Errors caused by other mods or by Minecraft itself are filtered out and never sent.

Reports are also de-duplicated and hard-capped at 10 events per game session.

## How to opt out

Set the following in `config/nerospace.properties` (created on first launch):

```properties
telemetryEnabled=false
```

This single switch covers **everything** the mod sends — error reports, release-health
sessions, performance samples, breadcrumbs, and the loaded-mod list alike.

The change takes effect immediately on config reload (or next launch) and no data is sent
while disabled. Server owners can opt out for the whole server the same way. Nothing is
ever sent before the config — and therefore your choice — has been loaded.

## In-world player data, and the NeroLink companion module

Separately from telemetry, Nerospace keeps the following personal data in the **world save on
your own server** (plus one short-lived in-memory entry) — nothing here leaves that server:

| Store | What it holds | Erasure |
|---|---|---|
| Station registry | the owner UUID of each orbital station and the UUIDs of the players its owner has added as members (up to 16) | the owner is blanked and you are removed from every member list; the backup is rewritten at once. The station, its class, modules and founding day stay as shared world content |
| Alien Villager reputation | a `UUID -> trade score` map inside each villager's entity data | swept from every loaded world; a villager that loads later drops your entry as it loads — in the same server session, or for up to 30 days afterwards (after a restart too) when the Village Core index still holds your erasure key (next row). No extra data is stored for this |
| Village Core ownership | the owner's UUID inside the core block's data (no name: the display name 1.x stored beside it is no longer kept and drops out of old saves the next time the core's chunk saves; chat shows a name only while that player is online) | cleared from every loaded core at once; a core in an unloaded chunk is cleared the moment it loads again, even after a server restart (see the next row). The core keeps its stockpile, buildings and quest and becomes unclaimed |
| Village Core index | where each claimed Village Core is (dimension and position) with a salted one-way hash of its owner's UUID, so erasure can reach a core whose chunk is not loaded. The hash is **pseudonymised, not anonymous**: it is never your UUID or a name, and nobody can turn it back into your UUID, but this server holds the salt and can recognise your hash. Plus, after an erasure, a list of core positions still to be cleared (positions only, at most 4096, each removed as soon as it is applied) and — only if you had visited a planet with villages — your hash as an **erasure key** (at most 256 keys, each deleted after 30 days), used for nothing but finishing your erasure: clearing a 1.x core that has not loaded since the update, and dropping your reputation from a villager that loads later. If any of these lists ever fills up, the server log shows a count-only warning | your rows are removed; your unloaded cores become position-only entries that are applied and deleted when they load; the backup is rewritten at once |
| Oxygen | your current air, in your player data | reset to a full tank |
| Star Guide "seen" markers | which guide steps you have dismissed | cleared |
| Planet visits | your UUID and the set of planets you have reached (no timestamps, no coordinates) | the row is dropped and the backup rewritten at once |
| Cargo routes | the owner UUID of each Cargo Pad, route and cargo flight, plus the UUIDs a pad owner shared their pad with; retention: completed flight records are pruned after 7 in-game days (`cargoFlightRetentionDays`) | your routes are removed, your pads and flights are unlinked from you (a pad stays as shared world content, cargo in the air is still delivered or crated — never deleted), and you are removed from every access list; the backup is rewritten at once |
| Launch cooldown (memory only) | your UUID and the game time you may launch again, for 5 seconds after a launch; never saved | dropped |

Everything else Nerospace saves holds **no personal data**: planet clocks and weather, the Nyxara
band width, per-block gravity overrides, launch and cargo pads' positions and labels, station
classes, modules and founding day, terraformers and their overlays, oxygen fields and external
oxygen contributions, and meteor events. Short-lived in-memory state (who is asleep near
Bio-Bark, the last planet synced to your client, magnetic-ore pulls, geyser grace) refers to
online players only, is never saved and disappears when you log out.
All of these are registered with Neroland Core's shared erasure hook, so one
`/neroland data eraseme` purges Nerospace along with every other Neroland mod. Two known
limits are stated plainly rather than glossed over: an Alien Villager in a chunk that is first
loaded again more than 30 days after your erasure (or after 256 later erasures pushed your key out)
can retain its reputation entry (re-running erasure after visiting the area clears it), and if you
are offline when the request is processed, your oxygen and Star Guide markers are reset the next
time you log in during that same server session.

**See your data:** `/nerospace privacy export` shows you — and only you — everything above that
Nerospace holds about you, as JSON you can copy: the planets you have reached, the stations you own
and the ones you are a member of, your Village Cores, Cargo Pads, routes and cargo flights, your oxygen and Star
Guide markers, and your reputation with loaded Alien Villagers. Positions and dimensions of your own
things are included; nothing about another player is (a station you own shows how many members it
has, never who they are).

The salvage drones at Mars Rover Wrecks keep no reputation and no record of who traded with
them, so there is nothing of yours to erase there.

If the **NeroLink companion bridge** is installed, Nerospace exposes a read-only view of
your own data to your paired companion client: your rockets and the launch pads around you,
the stations you own or are a member of, planet traits and which worlds you have reached, your
life support, and your Star Guide progress. Every section is filtered by the requesting player's
UUID — a station you neither own nor belong to, and another player's oxygen or progress, can
never appear in a response, and operator status is deliberately not honoured. Rockets and
pads have no owner in Nerospace, so that section reports only what you could already see
from where you are standing (a 128-block radius, while online) rather than a server-wide
list. The only two things a companion client can change are the name of a station you own
and the acknowledgement of your own alerts; nothing can launch a rocket, move a player or
edit the world remotely. The companion app can also read the Nerospace wiki pages bundled with
the mod; they are the same for every player and the request uses nothing about you.

The companion view of stations covers the stations you own or are a member of; member lists
are shown only to the station's owner and its members, and operator status is deliberately
not honoured. Members see each other's player ids there because they share that list — this is
deliberate: every member of a station can see who else may dock at it, exactly as in the in-game
console; names are never sent, and non-members never see the list. Only the owner can rename a
station from the companion app.

Server operators (permission level 2 and above) can rename, re-class, remove and build on any
station and manage its member list. Such operator actions are written to the server log with
the station's slot number and the action only — no player names, ids or station names. In
game, a station's member list is sent only to players who may use that station (its owner,
its members and operators); everyone else sees the member count alone and never the owner's
name.

Server owners can switch the whole module off in `config/nerospace.properties`:

```properties
linkModuleEnabled=false
```

### Progression gates (Neroland Core)

Nerospace also opens a handful of **player-scope progression gates** in Neroland Core's shared gate
store — personal milestones such as *First Freight* or *Terraformed Ground*, and two "hook" gates
another mod may open to hand you a Star Guide hint or an oxygen top-up. Each entry is your UUID plus a
gate id, held by Core on your own server and covered by Core's privacy notice and erasure hook; Nerospace
never logs the UUID. The world-wide freight count it publishes for shared quests is a plain number
labelled with a dimension id — never a pad position or a player.

### Optional economy fees and rewards (NeroEconomy)

When the optional **NeroEconomy** mod is installed **and** a server owner sets a non-zero
`economyFirstVisitReward`, `economyLaunchFee` or `economyDockingFee` (all default to `0` = off),
Nerospace asks NeroEconomy to pay or charge the player concerned. Nerospace stores **no new
per-player data** for this: your UUID is handed to NeroEconomy only for that one payment and is
never logged by Nerospace or placed in a request key (keys carry a planet id plus a world-wide
counter, or a cargo flight number). The planet-visit store gains one world-wide number — how many
first visits have ever been recorded — which is not tied to any player. The payment itself is a row
in NeroEconomy's ledger, labelled `nerospace/<reason>`; what NeroEconomy keeps, how long, and how it
is exported and erased is described in NeroEconomy's own privacy notice.

## Legal basis and your rights (GDPR / POPIA)

Error reports are processed on the basis of **legitimate interest** (GDPR Art. 6(1)(f);
POPIA s11(1)(f)): keeping the mod functional and crash-free, using the minimum data
necessary. The reports are engineered to contain no directly identifying personal
information, are stored in the EU, and are retained only as long as Sentry's standard
retention period (90 days) before automatic deletion.

If you believe a report contains personal data, or wish to exercise any data-subject
right (access, deletion, objection), contact:
**[info@neroland.co.za](mailto:info@neroland.co.za)**. Include the
approximate date/time of the crash so the matching event can be located and removed.

Sentry acts as a data processor; see the
[Sentry privacy policy](https://sentry.io/privacy/) and
[data processing addendum](https://sentry.io/legal/dpa/).

## Changes to this policy

If a future version of Nerospace ever collects additional data, this page will be updated
**before** that version is released, the change will be called out in the changelog, and the
same opt-out (`telemetryEnabled = false`) will continue to cover everything the mod sends.
The policy shipped alongside a given mod version describes exactly what that version does.

## Developer note: verifying telemetry locally

No env file or credentials are needed — the DSN is embedded. Launch a dev client with the
self-test flag and one synthetic event is sent on config load (environment matches the
version channel, with tag `runtime=dev`):

```text
./gradlew runClient -PtelemetryTest=true
```

or add `-Dnerospace.telemetry.test=true` to the IDE run config's VM args. Check the log for
"Telemetry self-test" and the event in the Sentry dashboard. Setting
`telemetryEnabled=false` in `run/config/nerospace.properties` and reloading must stop
events — that's the opt-out test.

For verifying a **release jar** end-to-end, the mod also registers a hidden diagnostic block,
`nerospace:sentry_test`. It does not appear in the creative menu and cannot be crafted — the
only way to obtain it is the command `/give @s nerospace:sentry_test`. Placing it sends a
single synthetic, clearly-labelled test event ("safe to ignore") through the exact same
pipeline — and therefore the same scrubbing, opt-out gate, and session cap — as a real error
report. If telemetry is disabled it sends nothing and says so in chat. Regular gameplay can
never trigger it.
